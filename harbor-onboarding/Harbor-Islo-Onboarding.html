01 · Mental model

What Harbor is

Harbor evaluates and optimizes AI agents inside isolated sandboxes. You point it at a dataset (or a single task), pick an agent and model, and it fans out trials — locally on Docker or on a cloud environment like Islo, Daytona, or Modal.

Task

One evaluation unit: instruction.md, task.toml, environment/, tests/, optional solution/.

Dataset

A named collection of tasks (e.g. terminal-bench@2.0) from the Harbor registry.

Agent

The program under test — Claude Code, Codex, OpenHands, Oracle, or a custom BaseAgent.

Environment

The sandbox provider. Docker by default; --env islo runs the same trial on an Islo microVM.

Trial / Job

A trial is one agent attempt at one task. A job is the cartesian product, run with concurrency.

Verifier & trajectory

Tests write a reward under /logs/verifier/. Agents emit ATIF trajectories for debug and training.

04 · Islo branch

Repos that branch from Harbor

GitHub fork of harbor-framework/harbor with upstream remotes. This is the Islo working branch of Harbor — same in-tree src/harbor/environments/islo.py, examples, and tests.

05 · Provider path

Run Harbor in an Islo environment

Same Harbor jobs — swap the sandbox. Authenticate with an Islo API key, then select the Islo environment type (bundled) or the plugin import path.

Recommended — Harbor with Islo extra

Uses the in-tree provider registered as type: islo.

pip install 'harbor[islo]'
# from a checkout: uv sync --extra islo

export ISLO_API_KEY=...          # required (Descope key or session JWT)
export ISLO_API_URL=https://api.islo.dev   # optional
export ISLO_COMPUTE_URL=...      # optional compute-plane override
export ANTHROPIC_API_KEY=...     # if your agent needs it

harbor run \
  --env islo \
  --dataset terminal-bench@2.0 \
  --agent claude-code \
  --model anthropic/claude-opus-4-1 \
  --n-concurrent 4

# Pass Islo-only constructor kwargs
harbor run --env islo \
  --environment-kwarg delete_after_seconds=7200 \
  --path examples/tasks/islo-network-policy-demo

Default sandbox image is docker.io/library/islo-runner:latest. Sandboxes auto-delete after 3600s unless you override delete_after_seconds (0 or a multiple of 60).

Plugin — independent Islo release train

From islo-labs/harbor-env. Useful when Islo needs to ship environment fixes faster than Harbor releases. 

pip install harbor-islo   # harbor >= 0.6, Python 3.12+

export ISLO_API_KEY=...

harbor run \
  --env harbor_islo:IsloEnvironment \
  --dataset terminal-bench@2.0 \
  --agent claude-code \
  --model anthropic/claude-opus-4-1
# job YAML
environment:
  import_path: "harbor_islo:IsloEnvironment"
  kwargs:
    gateway_profile: "prod-apis"

The plugin currently lags upstream on portable NetworkPolicy → gateway translation, delete_after_seconds, and DinD compose service ops. Prefer bundled --env islo unless you need the plugin release train.

Phased network policy on Islo

Harbor’s portable network policy becomes an ephemeral Islo gateway profile. The demo task keeps setup/verifier on the public baseline and restricts the agent phase. 

cd harbor   # upstream or harbor-fork checkout
export ISLO_API_KEY=...
export ANTHROPIC_API_KEY=...

uv run harbor run \
  -c examples/configs/environments/islo/network-policy-demo.yaml
# examples/configs/environments/islo/network-policy-demo.yaml
environment:
  type: islo
  force_build: false
  delete: true
  env:
    - ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY}

agents:
  - name: claude-code
    model_name: anthropic/claude-3-5-sonnet-20241022

tasks:
  - path: examples/tasks/islo-network-policy-demo

Islo allowlists support exact hostnames only (no wildcards, IPs, or CIDRs). Don’t combine network_mode=allowlist|no-network with a custom gateway / gateway_profile — Harbor can’t verify the profile matches the policy.

Named profile vs inline ephemeral gateway

Pick one — never both.

# Named profile (pre-created in Islo control plane)
environment:
  type: islo
  kwargs:
    gateway_profile: "prod-apis"

# OR inline rules → Harbor creates harbor-<session> ephemeral profile
environment:
  type: islo
  kwargs:
    gateway:
      default_action: "deny"
      internet_enabled: true
      rules:
        - host_pattern: "api.openai.com"
          action: "allow"
          provider_key: "openai"
        - host_pattern: "gist.github.com"
          action: "allow"

Ephemeral profiles enable dynamic_network_policy (phase switches during agent/verifier). Named profiles do not — Harbor won’t rewrite a shared production profile mid-trial.

06 · Code in detail

IsloEnvironment walkthrough

Canonical implementation: src/harbor/environments/islo.py (~1300 lines) in upstream and harbor-fork. Class: IsloEnvironment(ComposeServiceOpsMixin, BaseEnvironment). Longer write-ups live in docs/islo-environment.md.

Four start modes

IsloEnvironment.start() · islo.py

After _setup_gateway(), start() branches on the task’s environment/ definition:

  • Compose — docker-compose.yaml (or extra_docker_compose): sandbox = islo-runner with Docker capability → _start_compose() stages Harbor compose templates into /harbor/compose and runs the main service.
  • Prebuilt — docker_image set and no force-build: that image is the sandbox (init: minimal).
  • Dockerfile — build context uploaded, _build_and_run_docker() creates container task-env via DinD.
  • Bare — fallback plain islo-runner with no nested Docker.
await self._create_sandbox(
    image=_DEFAULT_IMAGE,  # or docker_image for prebuilt
    init={"type": "custom", "capabilities": ["docker"]},  # or minimal
    gateway_profile=gateway_profile_name,
)
await self._wait_for_running()  # poll get_sandbox every 2s, up to 60 tries

Sandbox lifecycle

_create_sandbox · _wait_for_running · stop · attach

_client()

Lazy AsyncIslo(api_key, base_url, compute_url, timeout=120).

_create_sandbox(image, init, gateway_profile)

Calls client.sandboxes.create_sandbox with vcpus/memory_mb/disk_gb from Harbor resource config. Optional lifecycle body: {delete_after: N}. Retries ×3 on RuntimeError; shields cancel so a half-created VM can still be cleaned up.

stop(delete)

Compose down or docker stop task-env, then _delete_sandbox, finally _cleanup_gateway (deletes ephemeral profiles only).

attach()

Replaces the process with islo use <sandbox> … — compose exec into main, DinD into task-env, or bare shell.

Gateway & network policy

GatewayConfig · _setup_gateway · _apply_network_policy

Harbor’s NetworkPolicy maps to Islo gateway egress:

  • PUBLIC → allow + internet
  • NO_NETWORK → deny + internet_enabled=False
  • ALLOWLIST → deny + allow rules per allowed_hosts
_setup_gateway()

Named profile returned as-is. Otherwise creates ephemeral harbor-<sanitized-session>, adds rules, stores profile/rule ids.

_apply_gateway_config(config)

Updates profile, deletes old rules, recreates, sleeps 2s for propagation — used when Harbor flips agent/verifier phase policies. 

capabilities.dynamic_network_policy = (
    self._gateway_profile is None and self._gateway_config is None
)

Exec and file transfer

exec · upload_* · download_*

  • _sandbox_exec — SDK exec_and_wait on the VM
  • _docker_exec — docker exec … task-env via the VM
  • _compose_main_exec — compose exec into main
  • exec() merges env/user, then picks compose → docker → sandbox

Uploads/downloads use a two-hop when the target isn’t on a bind mount: SDK stage to /tmp/harbor_<uuid> on the VM, then docker cp / compose cp into the task container. Paths under mounts, /tests, and /solution go straight through the SDK.

Constructor surface

IsloEnvironment.__init__

IsloEnvironment(
    gateway_profile: str | None = None,
    gateway: GatewayConfig | dict | None = None,  # XOR with profile
    delete_after_seconds: int = 3600,             # 0 or % 60 == 0
    **kwargs,  # BaseEnvironment: environment_dir, session_id,
               # task_env_config, network_policy, mounts, …
)
  • Reads ISLO_API_KEY, ISLO_API_URL, ISLO_COMPUTE_URL
  • Detects compose mode before super().__init__ (validation depends on it)
  • If no custom gateway, builds _network_policy_gateway_config from the task policy
  • Parses Dockerfile WORKDIR (default /app) when not in compose mode

Factory registration: EnvironmentType.ISLO → harbor.environments.islo:IsloEnvironment with pip extra islo (islo>=0.3.3, dockerfile-parse).

harbor-env plugin differences

harbor_islo/environment.py · package harbor-islo

  • Loaded via import_path, not type: islo
  • No portable NetworkPolicy translation / dynamic phase updates
  • No delete_after_seconds or ISLO_COMPUTE_URL
  • Still uses older init_capabilities + CA compose overlay for the gateway proxy
  • No ComposeServiceOpsMixin / sidecar helpers

Treat the plugin as a compatibility shim for faster Islo iteration; read the bundled islo.py when learning the full feature set.
